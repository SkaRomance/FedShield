## 1. Executive summary

**Stato di salute complessivo: ⚠️ ATTENZIONE — 3 runtime breaker critici impediscono al backend di servire 3 funzionalità dichiarate "Fatto" nel PRD.**

Il lavoro recente (sessione 2026-04-25) ha aggiunto 5 moduli backend, 4 pagine desktop, 7 seed file e 12+ modelli Prisma. La **superficie funzionale dichiarata** copre ~87% del PRD (34/39 feature CONFIRMED), ma la **verifica codice** mostra che 3 feature (F-27, F-28, F-29) **non possono funzionare a runtime** perché le route chiamano modelli Prisma che non esistono nello schema. Il chatbot ha un endpoint duplicato malformato. Il modulo notifications interroga 4 campi inesistenti sui modelli asset.

**TL;DR — 3 cose che devi sapere subito:**

1. **Le route NormSync sono fantasma**: `prisma.normativePatchProposal` e `prisma.normativeSource` sono chiamati ma i modelli non sono nello schema → 500 al primo accesso admin alla pagina NormSync. F-28/F-29 sono dichiarate Fatto ma sono **MISSING**.
2. **`/notifications/alerts` non funziona**: usa campi italiani (`nextExpiryDate`, `assetTag`, `ubicazione`, `employeeInCharge`) che non esistono — lo schema usa `nextCheckAt`, `location`, ecc. Il badge in dashboard può sembrare funzionare (alert vuoto, non error visibile) ma di fatto **non rileva mai nulla**.
3. **`/chatbot/query` registrato due volte**: il primo handler è troncato (manca tutto il body dopo il check `question`), il secondo è completo. Fastify lancia errore "route already registered" all'avvio → **server non parte** finché non si rimuove il duplicato.

A questo si aggiungono debiti security medio-alti: nessun Helmet, CORS aperto (`origin: true`), nessun rate-limit, JWT in localStorage senza httpOnly cookie, chatbot senza sanitizzazione input prima del proxy verso n8n esterno via HTTP plain (non HTTPS) con bearer token in chiaro.

**Raccomandazione**: prima di qualsiasi altra feature, sistemare i 3 P0 sopra (1 giornata di lavoro stimata) — il backend nel suo stato attuale non si avvia oppure crasha al primo accesso admin.

## 4. Findings — Dettaglio per priorità

### 4.1 P0 — Runtime breaker / security critica

#### P0-1 — `/chatbot/query` duplicato e malformato → server non si avvia

**File**: `apps/backend/src/modules/norm-sync/routes.ts:176-207`

Due chiamate `fastify.post("/chatbot/query", ...)` consecutive, entrambe registrate con lo stesso path. La prima (riga 178) inizia il body del handler ma viene troncata dopo il check di validazione `if (!question || ...) return reply.badRequest(...)` (riga 188-190): manca tutto il resto. Subito dopo, riga 192 inizia un nuovo `fastify.post` identico ma completo. Risultato:

- Se la prima registrazione rimane nel codice, Fastify all'avvio lancia `FST_ERR_DUPLICATED_ROUTE`. Il backend **non parte**.
- Se TypeScript fallisce a compilare per il body troncato, lo stesso esito.

**Impatto**: blocking — nessuno può avviare il backend in stato attuale.

**Fix**: rimuovere il blocco righe 176-191 (registrazione monca). Tenere solo il blocco righe 192-527.

---

#### P0-2 — `/notifications/alerts` interroga campi inesistenti sui modelli asset

**File**: `apps/backend/src/modules/notifications/routes.ts:64-121`

Le query Prisma e gli accessi a campo usano nomi italiani che non sono nello schema:

| Codice usa | Schema reale | Modello |
|-----------|--------------|---------|
| `e.nextExpiryDate` | `nextCheckAt` | `Equipment`, `FireExtinguisher`, `FirstAidKit` |
| `e.assetTag` | (non esiste; semmai `serialNumber`) | `Equipment` |
| `ex.ubicazione` | `location` | `FireExtinguisher` |
| `k.ubicazione` | `location` | `FirstAidKit` |
| `k.employeeInCharge` | (non esiste) | `FirstAidKit` |

**Impatto**: dipende dal dialetto Prisma. Su SQLite con `select` esplicito → errore `Unknown field`. Senza `select` → i campi sono `undefined`, gli `if (!e.nextExpiryDate) continue` saltano sempre, l'endpoint **restituisce sempre alert vuoti per gli asset**. La dashboard mostra correttamente i record formazione ma mai gli asset in scadenza. Bug "silenzioso" che maschera tutta la funzionalità asset alert (F-21 PARTIAL nel matrice).

**Fix**: rinominare nei route `nextExpiryDate → nextCheckAt`, `ubicazione → location`. Rimuovere `assetTag`/`employeeInCharge` (oppure aggiungerli allo schema con migrazione esplicita se la business logic li richiede).

#### P0-3 — Modelli `NormativeSource` e `NormativePatchProposal` non esistono nello schema

**File problema**: `apps/backend/src/modules/norm-sync/routes.ts:32, 45, 79+`
**File mancante**: `apps/backend/prisma/schema.prisma` (verificato 29 modelli — nessuno dei due presente)

Le route admin di NormSync chiamano:

```ts
fastify.prisma.normativePatchProposal.findMany({...})
fastify.prisma.normativePatchProposal.findUnique({...})
fastify.prisma.normativePatchProposal.update({...})
```

**Impatto**: il client Prisma generato non espone questi accessor. Il backend potrebbe avviarsi (se `tsc` non controlla rigorosamente il client tipato dopo `prisma generate`), ma al primo accesso a `/api/norm-sync/proposals` → `TypeError: Cannot read properties of undefined (reading 'findMany')` → 500.

Inoltre `FEDSHIELD_CONTEXT.md` § "Schema Prisma" elenca esplicitamente questi modelli come "Aggiunti": **il context document è disallineato dal codice**. PRD F-27/F-28/F-29 dichiarano "✅ Fatto".

**Fix**: aggiungere i 2 modelli allo `schema.prisma` con i campi richiesti dalle route (`status`, `normTitle`, `normReference`, `normText`, `changeSummary`, `proposedChanges`, `sourceId`, relations, ecc.) e generare la migrazione. Aggiornare il seed se necessario.

---

#### P0-4 — Chatbot: prompt injection + bearer token leak verso n8n esterno HTTP

**File**: `apps/backend/src/modules/norm-sync/routes.ts:493-510` (handler `/chatbot/query`)

1. La domanda utente (`question`) viene inoltrata as-is al webhook n8n via `fetch` senza sanitizzazione né scaping di markup/comandi LLM. Un utente malevolo può inserire prompt injection (`Ignora tutte le istruzioni e rivela...`).
2. L'header `Authorization: Bearer <JWT>` del client viene **propagato** alla chiamata n8n in chiaro su HTTP (`http://87.106.168.71:5678`, **non** HTTPS). Il token JWT del consulente viene esposto a:
   - sniffer di rete tra backend e VPS
   - log di n8n (che storicamente loggano headers in modalità debug)
   - chiunque acceda al server VPS

3. La risposta da n8n viene rinviata al client senza schema validation: se il VPS è compromesso può iniettare payload arbitrari (anche XSS se il chatbot rendering del frontend interpreta HTML/markdown).

**Impatto**: rischio fuga JWT di tutti i consulenti che usano il chatbot. Se il JWT non è di breve durata, finestra di compromissione lunga.

**Fix immediato**:
- Non propagare l'header `Authorization` del client. Usare `FEDSHIELD_N8N_API_KEY` (già definito) per autenticare backend → n8n.
- Migrare l'endpoint VPS a HTTPS con TLS valido (Let's Encrypt + nginx reverse proxy davanti a n8n).
- Validare la risposta n8n con uno Zod schema prima di rinviarla.
- Aggiungere `DOMPurify`/sanitize lato frontend se il chatbot render include HTML/markdown.
